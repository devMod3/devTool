ENTORNO DE DESARROLLO / WORKSPACE / STACK TECNOLÓGICO
VIBE CODING — MAPA DE RESPONSABILIDADES
Estado de referencia: 2026-08-29/30
Ámbito: desde la conversación con el agente hasta una página publicada y verificable.

OBJETIVO

Este documento fija el entorno operativo de vibe coding como una cadena de responsabilidades. No define el producto por una herramienta concreta: identifica qué componente toma decisiones, cuál modifica el repositorio, cuál ejecuta código, cuál valida, cuál construye y cuál publica.

La fuente de verdad del producto es GitHub y la evidencia ligada a un SHA. La conversación sirve para dirigir el trabajo; no reemplaza Git, CI ni los artefactos verificables.

FLUJO END-TO-END

Usuario
  -> ChatGPT
  -> conector @GitHub
  -> repositorio y rama de trabajo
  -> commit
  -> Pull Request
  -> GitHub Actions / CI
  -> merge a main
  -> workflow de producción
  -> build estático
  -> artefacto GitHub Pages
  -> deployment
  -> página web
  -> ResurrecciónLLM captura el nuevo estado verificable

1. USUARIO / INTENCIÓN

Responsabilidad:
Define objetivo, restricciones, prioridades y autorización de cambios.

Dónde actúa:
En la conversación.

Qué problema resuelve:
Aporta intención humana. Ningún workflow puede decidir por sí solo qué producto se quiere construir.

Regla:
La intención puede cambiar; el estado técnico no se supone. Antes de actuar sobre un proyecto existente se revalida GitHub.

2. CHATGPT / AGENTE DE ORQUESTACIÓN

Responsabilidad:
Traducir intención a diagnóstico, plan, cambios de código, revisión, validación y explicación.

Dónde actúa:
En la conversación y a través de herramientas autorizadas.

Configuración observada en esta sesión:
GPT-5.6 Sol.

Qué problema resuelve:
Coordina trabajo multidisciplinario sin convertir la memoria del chat en fuente de verdad.

Regla:
El modelo no es una dependencia de build del producto. Puede cambiar en el futuro. La continuidad durable debe quedar en GitHub, no únicamente en la conversación.

3. CONECTOR @GITHUB

Responsabilidad:
Canal autenticado entre el agente y GitHub.

Dónde actúa:
Repositorios, archivos, blobs, árboles Git, commits, ramas, Pull Requests, reviews y GitHub Actions.

Qué problema resuelve:
Permite que el agente lea y modifique estado real sin copiar credenciales al código o a la conversación.

Regla de seguridad:
Tokens, cookies, secretos y cabeceras Authorization no se persisten en CONTINUITY_STATE.json, documentación ni artifacts.

Regla de evidencia:
Una afirmación sobre CI, PR, branch, commit o deployment debe resolverse contra GitHub actual cuando sea material.

5. RESURRECCIÓNLLM

Ubicación:
devMod3/devTool/ResurrecciónLLM

Workflow ejecutable:
devMod3/devTool/.github/workflows/continuity-snapshot.yml

Responsabilidad:
Reconstruir el estado verificable de cualquier repositorio después de pérdida de contexto.

Qué observa:
HEAD exacto.
Rama por defecto.
Ref objetivo.
PRs abiertos.
Hint de working branch si se proporciona.
Hint de PR si se proporciona.
Check-runs ligados al SHA.
Workflow-runs ligados al SHA.
Deployment ligado al SHA.
Cambio respecto al snapshot anterior.

Qué persiste:
CONTINUITY_STATE.json en devTool.

Modelo de ownership:
La máquina administra snapshot, drift e history.
El agente administra continuity.

Estados de drift:
INITIAL: primera observación.
FRESH: continuidad del agente ligada al HEAD actual.
STALE: el HEAD cambió desde el plan guardado.
UNBOUND: existe continuidad, pero no está ligada a un SHA.

Qué problema resuelve:
Evita continuar desde PRs, ramas, errores o planes que fueron ciertos en una sesión anterior pero ya no representan GitHub.

Regla:
CONTINUITY_STATE.json central vive en devTool. No debe duplicarse en la raíz de los repositorios observados.

38. CICLO DE CONTINUIDAD RECOMENDADO

Inicio de sesión:
Ejecutar ResurrecciónLLM contra el repositorio objetivo cuando el contexto previo pueda estar desactualizado.

Durante la sesión:
Trabajar en branch y PR.
No actualizar manualmente el snapshot machine-owned.

Después de merge/deploy importante:
Ejecutar ResurrecciónLLM nuevamente.

Fin de sesión:
Dejar continuity ligada al SHA real y un next_action observable.

Nueva sesión:
Leer el registro central.
Revalidar GitHub.
Si drift es STALE o el HEAD difiere, reconstruir antes de actuar.
